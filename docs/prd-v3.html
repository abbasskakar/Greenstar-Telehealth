Product Requirements Document · Unified & Superior

Greenstar Telehealth

A field-first digital health platform that puts a doctor within reach of the last mile — capturing vitals, voice, and location in a remote village and connecting instantly to an available clinician, even over weak connectivity.

Version 3.0 Status Draft for review Date 17 Aug 2026 Supersedes v1 + v2
Purpose of this document

This PRD unifies every capability from the two earlier requirement sets, closes the functional and workflow gaps found in both, tightens the system into one coherent product, and removes anything redundant or over-specified. Each feature is scoped to be built — with clear behaviour and acceptance criteria — and written to reassure donors and NGO leadership that this is a mature, field-ready platform.

01

Executive Summary

Greenstar Telehealth connects community health workers (LHV / Nurse / CMW), remote doctors, program administrators, and the general public into a single real-time system. A health worker in a remote village can capture a patient's condition — vitals, history, voice, location — and instantly reach an available doctor for a video consultation, a clinical note, or an e-prescription.

Beyond individual care, it is an NGO program-management platform: it tracks field coverage on a map, runs community health camps, measures emergency response times, and produces donor-ready reports automatically.

What makes v3 better than both prior documents

1A real patient record

A longitudinal Patient Registry ties every visit, vital, note, and prescription to one identity — the foundation both prior PRDs were missing.

2Closed-loop clinical flow

Consultation → e-prescription → lab/diagnostic request → follow-up → outcome. The earlier PRDs stopped at “notes.”

3Reliable emergency routing

A claim-and-lock model plus an escalation chain (online doctors → SMS → supervisor) so an emergency is never dropped or double-handled.

4Bilingual, low-literacy UX

English + Urdu and voice-first patterns for the real users — absent from both prior versions.

5Privacy & consent built in

CNIC is sensitive PII: encryption, masking, audit, retention, and erasure controls throughout.

6Interoperability path

DHIS2 / FHIR-lite export so program data flows into national and donor health systems.

Users, Roles & Permissions

Personas

  • Provider (LHV / Nurse / CMW) — a field health worker, often on a low-end phone with intermittent data. Needs speed and simplicity.
  • Doctor — a remote clinician handling many cases. Needs rich patient context fast and strong triage tools.
  • Admin — manages accounts, security, and system health.
  • Program Manager New — owns camps, coverage, reports, and donor deliverables. Read-heavy, not technical.
  • Public User — self-registers with CNIC to book their own consultations.

04

Product Scope

In scope

Authentication & onboarding · Patient Registry · Appointments & triage · Real-time notifications · Video consultation · Clinical notes (text + voice) · E-prescriptions · Lab/diagnostic requests · Vitals monitoring & trends · Online/Offline duty · Geo-tagging & coverage maps · Camps & events · Reporting & donor analytics · Admin & user management · CNIC public registration · Consent & privacy · Offline-first sync · Bilingual UX · PWA (web) + React Native (mobile).

Out of scope — explicitly deferred

  • Payments / billing / insurance claims.
  • Pharmacy inventory & dispensing logistics (only prescription authoring is in scope).
  • Full EHR/HL7 hospital integration — we ship an export path, not live bidirectional integration.
  • AI diagnosis. Transcription/summarisation are optional aids, never diagnostic.

Removed / simplified from prior PRDs

No more 5s polling

Hard “auto-refresh every 5 seconds” → realtime subscriptions, with 5s polling kept only as a fallback. Constant polling drains field-phone battery and data.

No fixed UI counts

“23+ appointments”, “27+ specialties” treated as guidance, not requirements. Lists are paginated and virtualised.

No re-typing patients

Per-appointment patient data → a reusable patient record, enabling history and vital trends.

Information Architecture & Data Model

Core entities, implemented in PostgreSQL/Supabase with RLS. The shift from the prior PRDs is a true Patient entity at the centre — one patient, many appointments, each carrying its own vitals, notes, prescriptions, and lab requests.

User

role, name, phone, specialty, duty_status, created_by, is_active.

Patient Core

MRN, CNIC (encrypted), demographics, language. One patient → many appointments.

Appointment / Case

patient_id, type, specialty, status, assigned_doctor, geo, camp_id, consent_id.

VitalSet

BP, HR, temp, SpO2, hemoglobin, blood sugar — time-series, enables trends.

Note

kind (text/voice), body/audio_ref, transcript. Thread per appointment.

Prescription New

structured items (drug, dose, frequency, duration), advice, follow-up, signed.

LabRequest New

tests[], status (requested/resulted), result_files, result_note.

Consent

type, granted_by, method, timestamp — tied to patient/appointment.

Camp / Event

type, date_range, location, team, turnout, counters, photos, status.

Notification

type, payload, channel (push/sms/in-app), delivered_at, ack_at, read_at.

AuditLog

actor, action, entity, before/after, timestamp, device.

Relationships: Patient 1—∗ Appointment 1—∗ {VitalSet, Note, Prescription, LabRequest}; Appointment ∗—1 Camp (optional); Appointment 1—1 Consent.

06

Feature Requirements

Each module states behaviour and its key acceptance criteria (AC).

6.1 Authentication & Onboarding

  • Role-based login for all five roles; staff accounts are admin-created (no open staff self-signup).
  • Public self-registration via 13-digit CNIC (validated + unique) + flexible username + password.
  • JWT sessions (8-hour expiry), Bcrypt hashing, secure forgot-password flow.
  • Optional 2FA (OTP) for Admin and Doctor roles.
  • First-run guided onboarding for field workers: language pick, permission grants (mic, location, notifications), 60-second tour.
AC  Invalid/duplicate CNIC is rejected clearly · logged-out users reach no authenticated screen · a submitted-but-unsynced form survives session refresh.

6.2 Patient Registry Gap closed

  • Register a patient once; reuse the record on every later visit. Search by CNIC, MRN, name, or phone before creating a new one.
  • Profile shows demographics, vital-trend charts, appointment history, prescriptions, lab results, and a notes timeline.
AC  Creating an appointment offers “find existing patient” first · duplicate CNIC is caught · a doctor sees prior visits and vital trends.

6.3 Appointment & Case Management

Providers/Public create appointments with full patient data, mark Emergency/Regular, attach text or voice history, record 6 vitals, pick from 27+ specialties, and auto geo-tag. Doctors get a prioritised queue with filters and full patient context.

Triage, queue & assignment Improved

Cases order by (1) emergency flag, (2) time waiting, (3) specialty match — each showing a live “waiting for X:XX” timer. The first doctor to Accept/Claim locks the case; others see “Being handled by Dr. ___.” If the call isn’t started within a timeout, the case returns to the pool and re-broadcasts.

AC  Two doctors cannot both claim one emergency · an unclaimed emergency re-enters the queue after timeout · status transitions are audit-logged.

6.4 Real-Time Notification System

Instant push (Facebook/Instagram-style), delivered even when the app is closed (FCM / Service Worker), click-to-open the exact case, rich patient/vitals content, multi-device.

Emergency · persistent Regular appointment Incoming video call New note Status update Prescription / lab ready

Escalation chain Improved: online doctors → SMS fallback to on-roster doctors (if unacknowledged in a configurable 30–60s window) → alert the on-call supervisor. An emergency is never silently dropped.

Honest platform note

Web push on iOS Safari has OS-level limits. For emergencies, SMS is the guaranteed channel — this is a design decision, not an afterthought, given unreliable field connectivity.

AC  An unacknowledged emergency triggers SMS · delivery + ack + read are timestamped · tapping a call notification opens the ringing screen.

6.5 Video Consultation

  • One-tap Jitsi call (browser-based, no download); doctor auto-assigned as moderator.
  • Full-screen WhatsApp-style incoming call with ringtone, Accept/Decline; HD + screen share; call history + re-dial.
  • Low-bandwidth auto-fallback to audio-only / reduced resolution instead of dropping.
  • In-call context panel — vitals/history beside the video. Optional consent-gated recording for medico-legal record.
AC  Consent is checked before any recording · a throttled connection degrades rather than ends · call start/end feed response-time metrics.

6.6 Clinical Notes — Text & Voice

Bidirectional, appointment-specific, chat-style thread. Text (1000 chars) and/or voice notes: record via mic, offline-first (record offline → auto-upload on reconnect), in-app player with waveform, ~2 min max, optional auto-transcription clearly marked as generated.

AC  A voice note recorded offline uploads automatically on reconnect · transcription appears under the audio, labelled “auto-generated.”

6.7 E-Prescription Gap closed

Doctors write structured prescriptions (medicine, dose, frequency, duration, instructions) plus advice and an optional follow-up date, with a common-drug quick-pick and an advisory duplicate/allergy flag. Rendered as a clean, bilingual printable PDF and stored in patient history.

AC  A prescription renders as a shareable PDF with patient, doctor, date, items · appears in the longitudinal record · only Doctors can author.

6.8 Lab / Diagnostic Requests Gap closed

Doctor requests tests (checklist + free text); provider or public user uploads results/photos; doctor is notified when resulted. Results attach to the appointment and patient record.

AC  A request moves requested → resulted · uploaded files are viewable in-context · the doctor is notified on upload.

6.9 Vital Signs Monitoring & Trends

Six parameters — BP, HR, Temperature, SpO2, Hemoglobin, Blood Sugar — with icons and colour coding, plus trend charts across visits enabled by the patient registry.

Normal Borderline Abnormal
AC  Out-of-range values are auto-flagged · trends render when ≥2 vital sets exist.

6.10 Online / Offline Duty Status

Doctors & Providers toggle On Duty / Off Duty. Only On-Duty doctors receive emergency routing and appear in the active roster; auto-Off after configurable inactivity; Admin/PM see a live roster.

AC  Emergencies route only to On-Duty doctors · inactivity flips status · the roster updates in real time.

6.11 Geo-Tagging & Coverage Mapping

Every provider appointment auto-captures GPS (~20–50 m accuracy — area/village-level, not pinpoint). Admin/PM get a live map with colour-coded pins, clickable summaries, filters, and a coverage heat map of reached vs. underserved areas that feeds donor reports.

AC  New provider appointments appear as pins · the heat map reflects density · filters recompute the map.

6.12 Camps & Community Events

A module for organised outreach — Health Camp, Blood Donation, Vaccination Drive, Awareness Session. Records type, date, location, team, expected vs. actual turnout. Field staff log type-specific counters (patients seen, blood units, vaccines), photos, and linked appointments. Admin/PM get a calendar + map, roll-up stats, exportable donor reports, and optional light stock tracking for consumables.

AC  Camp-time appointments link back to the camp · counters roll up into quarterly stats · a camp report exports to PDF/Excel.

6.13 Admin & User Management

Create/manage Doctor, Provider, and Program Manager accounts; assign roles/specialties; generate/reset passwords; enable/disable/delete; monitor public registrations. Full audit logs of every create/update/delete, plus device/session management (force-logout a lost device) and system/security settings.

AC  Every destructive action is audit-logged · a disabled user cannot authenticate · Admin can force-logout a session.

6.14 Reporting & Donor Analytics

Automated monthly/quarterly reports (PDF/Excel): patients served by region/gender/specialty, emergency response metrics, doctor/provider utilisation, coverage + heat map, and camp summaries. A KPI dashboard for managers, and an interoperability export aligned to DHIS2 / FHIR-lite New so indicators flow into national/donor systems without re-entry.

AC  A quarterly report generates without manual entry · the response-time metric matches audit timestamps · export produces a valid DHIS2/FHIR-lite payload.

6.15 Consent & Privacy

Digital consent (timestamped) before consultations; CNIC and health data encrypted at rest and masked in UI (last 4 shown); RLS access control; a data retention policy and right-to-erasure workflow; consent required before any recording.

AC  No consultation proceeds without a consent record · CNIC is never shown in full to unauthorised roles · erasure requests are logged and honoured.

6.16 CNIC-Based Public Registration

13-digit CNIC validation + uniqueness, flexible username, encrypted storage, CNIC as the public login identifier.

AC  Non-13-digit or duplicate CNIC is rejected · CNIC is stored encrypted.
07

End-to-End Workflows

7.1 Emergency Improved

  1. Provider records vitals + optional voice note; consent captured.
  2. Provider creates an EMERGENCY appointment (location auto geo-tagged).
  3. System broadcasts to all On-Duty doctors within 3 seconds.
  4. The first doctor to Accept locks the case; others see it is handled.
  5. If unacknowledged → SMS fallback → supervisor escalation.
  6. Doctor reviews context and starts the video call; provider answers full-screen.
  7. Doctor examines, writes note + e-prescription (and lab request if needed).
  8. Provider carries out instructions; marks the case Completed. Response-time metrics logged automatically.

7.2 Regular

Provider or public user creates a regular case → doctor reviews at convenience → note/prescription → provider communicates to patient → follow-up scheduled if needed.

7.3 Public User

Self-register via CNIC → create own appointment → doctor reviews, sends note/prescription → user reads results and can ask follow-up questions.

7.4 Health Camp

Admin/PM schedules a camp → field team runs it, logging counters + photos → appointments during the camp auto-link → camp marked complete → data flows into donor reports.

7.5 Offline Field Capture New

Provider records vitals/history/voice offline → data queues locally → on reconnect, auto-syncs with a conflict-safe merge → the doctor sees it as normal.

Non-Functional Requirements

Performance

Core screens interactive < 2.5s on a low-end Android over 3G; lists virtualised.

Scalability

Unlimited concurrent users; realtime fan-out sized for peak emergency broadcast.

Security

JWT (8h), Bcrypt, RLS, TLS, encryption at rest for PII/CNIC, full audit logs, optional 2FA, session/device management.

Privacy & compliance

Consent-first, retention + erasure, least-privilege roles, PII masking. HIPAA-inspired; aligned to applicable Pakistani norms.

Emergency reliability

Guaranteed delivery via push → SMS → supervisor escalation.

Reach & localisation

Android (low-end priority), iOS, desktop browsers; English + Urdu at launch, ready for more.

What v3 Adds Over v1 & v2

Everything from both is kept. On top, v3 adds the following — and simplifies away what no longer serves field users.

Added capabilities

Patient Registry & longitudinal history · vital trends · e-prescriptions · lab/diagnostic requests · triage queue + claim/lock assignment · escalation chain beyond SMS · Program Manager role · consent/privacy/retention/erasure · bilingual + low-literacy UX · accessibility · DHIS2/FHIR-lite interoperability · in-call context panel · optional consultation recording · light camp stock · session/device management + optional 2FA.

Simplified / removed

Rigid 5-second polling → realtime + fallback. Fixed UI counts → paginated, virtualised lists. Per-appointment re-entry of patient data → a reusable patient record.

In one line

v1 was a basic clinical telehealth app; v2 was a strong NGO field platform; v3 is a complete, closed-loop, field-hardened health system — clinically deeper, operationally more reliable, and demonstrably donor-ready.
